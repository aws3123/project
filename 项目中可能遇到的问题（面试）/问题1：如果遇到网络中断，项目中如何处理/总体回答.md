"好问题！Java 层负责 可靠投递和状态管理 ，Python 层负责 自身熔断和依赖监控我们系统设计了 8层容错机制 来应对网络中断。我给你举个完整的例子：

## 📋 完整流程示例 

## 1️⃣ 请求进入

首先，用户通过前端发起一个代码审查请求，后端 ReviewController 接收请求。

##  2️⃣ 超时控制 - 防止无限等待

系统立即创建 ReviewTask ，状态设为 PENDING 。在调用 Python 服务时，我们配置了三层超时：

- 连接超时： 3秒（连不上就不等了）

- 读写超时： 60秒

- 整体超时： 同步120秒/异步180秒
  这样就不会因为网络中断导致请求无限挂起。

  3️⃣ Outbox 模式 - 确保事件至少投递一次

  为了保证消息不丢失，我们不直接发 MQ，而是：

- 先把事件写入 outbox_event 表，状态 PENDING

- 这一步和任务创建在同一个事务里，原子性保证

- 然后 OutboxPoller 每2秒扫描一次，把 PENDING 事件发往 MQ 

  4️⃣ MQ 重试 - 消息队列自动重试
  消息进入 Kafka 后，消费者 ReviewTaskConsumer 开始处理。

- 如果网络中断导致处理失败，Spring Cloud Stream 会自动重试

- 配置了 3次重试 ，退避策略：2s → 4s → 8s

- 每次重试前都会检查是否已经处理过（幂等性） 5️⃣ 幂等性 - 防止重复处理
怎么保证重试不重复处理呢？

- 每次消费前，先查 consumed_message 表，看这个消息 ID 有没有处理过

- 处理完了就把消息 ID 存进去

- 重复的消息直接跳过 6️⃣ 服务发现 - 自动切换可用实例
在调用 Python 服务时：

- PythonServiceRegistry 维护了可用实例列表

- 如果当前实例网络不通，自动切换到下一个健康实例

- 配合健康检查，只把流量发给健康的节点 7️⃣ DLQ - 超过重试次数的兜底处理
如果重试3次都失败（比如网络一直中断）：

- 消息自动进入 死信队列（DLQ）

- DlqConsumer 消费 DLQ，把任务状态设为 FAILED

- 记录错误原因："MQ_RETRY_EXHAUSTED" 8️⃣ 对账任务 - 定时扫描和恢复卡住的任务
但万一连 Outbox 都没发出去，或者 MQ 丢消息了呢？

- 别担心， ReconciliationJob 每分钟都在扫描：
  - 卡住的 PENDING 任务： 超过30分钟还没处理 → 重建 Outbox 事件
  - 超时的 PROCESSING 任务： 超过2倍超时时间还没完成 → 标记 FAILED 9️⃣ 健康监控 - 实时监控服务状态
整个过程中，我们通过 Actuator 实时监控：

- Python 服务健康状态

- Redis 连接

- Kafka 连接

- 有问题及时告警，运维能快速介入
### 🎯 总结
"所以这8层机制是 层层递进、互为补充 的：

1. 超时控制先把边界划好
2. Outbox + MQ 保证消息可靠投递
3. 服务发现自动切流量
4. 幂等性防止重复
5. DLQ 兜重试失败的底
6. 对账任务兜最极端的情况
7. 健康监控让问题可观测
这样即使网络不稳定，任务要么成功完成，要么正确失败，绝对不会丢！"
