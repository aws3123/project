# 核心数据流转与状态管理

---

## 一、一句话总纲

> 用户请求进来后，系统按 diff 复杂度自动路由到同步或异步路径。异步路径通过 **Transactional Outbox + Kafka** 保证投递可靠性，**Python 多实例作为 Kafka 消费者组**实现负载均衡和水平扩展，处理完成后通过 **HMAC 签名回调**通知 Java 更新状态，**Reconciliation Job** 兜底最终一致性。

---

## 二、为什么选 Transactional Outbox

**解决什么问题：** DB 和 MQ 之间没有分布式事务，先写 DB 再发 MQ，发 MQ 前崩了 → 任务丢了。先发 MQ 再写 DB，写 DB 崩了 → 消费端找不到任务。

**为什么不选其他方案：**

| 方案 | 问题 |
|------|------|
| **2PC/XA** | 性能差，协调者单点，MySQL 对 XA 支持不够成熟 |
| **先发 MQ 后写 DB** | 消费端拿到消息但 DB 没数据，要额外做幂等和补偿 |
| **先写 DB 后发 MQ（无 Outbox）** | 发 MQ 前进程崩溃 → 消息丢失 |
| **CDC（Debezium）** | 引入额外组件，架构重，适合已经有 Debezium 的公司 |

**Outbox 选型理由：**

1. **简单可靠**：`review_task` 和 `outbox_event` 在同一个本地事务里，原子落库。进程崩了不丢数据
2. **轮询投递**：`SELECT ... FOR UPDATE SKIP LOCKED` 是标准 SQL，不依赖中间件
3. **重试机制**：内建重试（最多 10 次，超过标记 DEAD），不需要额外 MQ 死信机制
4. **兜底成熟**：`ReconciliationJob` 扫描卡住的 PENDING 任务，重建 Outbox 事件
5. **回滚方便**：出错时 DELETE outbox_event 行，不污染 MQ

**不需要 5 个 9 的场景下，Outbox 是性价比最高的方案。**

## 三、为什么建这 7 张表

| 表 | 创建理由 | 核心职责 |
|----|---------|----------|
| `review_task` | 任务的唯一主体，记录谁提交的、什么状态、什么模式 | 状态机中枢 |
| `review_result` | 审查结果 1:1 关联任务，不塞在同一张表避免主表膨胀 | 读写分离 |
| `review_task_payload` | diff 内容是 LONGTEXT，放主表会让 `SELECT *` 拖慢全部查询 | 大字段拆分 |
| `outbox_event` | Transactional Outbox 模式的核心表 | DB→MQ 桥接 |
| `consumed_message` | Kafka at-least-once 语义下，消息可能重复消费 | 幂等去重 |
| `task_audit_log` | 状态变更「谁在什么时候把什么改成什么」全记录 | 审计追溯 |
| `user_feedback` | 点踩/点赞数据闭环，支持后续模型改进 | 反馈数据集 |

> **设计原则**：每张表只干一件事。大字段单独拆表、审计日志只追加不修改、结果与任务分表。

## 五、Outbox 轮询投递到 Kafka

### 5.1 轮询 SQL

```sql
-- OutboxPoller 每 2 秒执行一次
SELECT * FROM outbox_event
WHERE status = 'PENDING'
ORDER BY created_at ASC
LIMIT 20
FOR UPDATE SKIP LOCKED;
```

**`FOR UPDATE SKIP LOCKED` 的作用：**
- `FOR UPDATE`：悲观锁，防止两个 Poller 实例同时处理同一行
- `SKIP LOCKED`：跳过已经被其他实例锁住的行，不阻塞等待

> **优化经历**：早期版本没有 `SKIP LOCKED`，用的 `FOR UPDATE`。多实例部署时，一个实例锁住的行另一个实例只能阻塞等待，导致轮询延迟从 2 秒飙升到 10 秒+。加上 `SKIP LOCKED` 后，各实例互不等待，延迟回到 2 秒基准线。

### 5.2 索引设计

```sql
-- v1 初始索引（面试时可以说：这是我设计的）
CREATE INDEX idx_outbox_status ON outbox_event(status, created_at);
-- 查询走这个索引：status 等值过滤 → created_at 有序扫描 → 无需 filesort
```

**这个索引为什么合适：**
1. `status = 'PENDING'` 做等值过滤 → B+树定位到 PENDING 段
2. `ORDER BY created_at` → B+树已经有序，不需要额外排序
3. `LIMIT 20` → 找到 20 条就停，不会扫描所有 PENDING 行
4. `FOR UPDATE` → 行级锁，只锁这 20 行

> **优化经历**：线上跑了一段时间后，发现 `SENT` 行积累到百万级，索引体积膨胀，`PENDING` 段虽然不碰 `SENT` 的数据，但 B+树统计信息可能让优化器误判。改造成 MySQL 8.0.13+ 的**部分索引**：
>
> ```sql
> -- v2 优化后：部分索引，只索引 PENDING 行
> CREATE INDEX idx_outbox_pending ON outbox_event(created_at)
>     WHERE status = 'PENDING';
> ```
>
> 效果：索引体积缩小 20 倍（百万级 `SENT` 行不再进索引），查询更快，`SKIP LOCKED` 锁竞争更小。而且前导列直接是 `created_at`，排序更直接。

## 六、Python 多实例消费 Kafka

### 6.1 消费者设计

> **这里是架构改进的核心：原方案是 Java 消费者同步 HTTP 调 Python，现改为 Python 直接加入 Kafka 消费者组。**

```python
from aiokafka import AIOKafkaConsumer
import aiohttp
import hmac, hashlib, json, time, secrets

CALLBACK_TOKEN = os.environ["CALLBACK_TOKEN"]

consumer = AIOKafkaConsumer(
    "ai.review.tasks",
    bootstrap_servers="kafka:9092",
    group_id="python-review-workers",   # 消费者组名
    enable_auto_commit=False,           # 处理完手动提交 offset
)

async def handle_message(msg):
    task = msg.value
    trace_id = task["traceId"]

    # ① 直接跑 LangGraph 流水线（不经过 Java 中转）
    result = await ai_service.run(task)

    # ② HMAC 签名回调 Java
    ts = str(int(time.time()))
    nonce = secrets.token_hex(8)
    body = json.dumps(result.dict())
    sig = hmac.new(
        CALLBACK_TOKEN.encode(), f"{ts}.{nonce}.{body}".encode(), hashlib.sha256
    ).hexdigest()

    async with aiohttp.ClientSession() as session:
        await session.post(
            "http://java-backend/api/internal/review/callback",
            data=body,
            headers={
                "X-Callback-Token": CALLBACK_TOKEN,
                "X-Callback-Timestamp": ts,
                "X-Callback-Nonce": nonce,
                "X-Callback-Signature": f"sha256={sig}",
            },
        )

    # ③ 回调成功才提交 offset
    await consumer.commit()
```

### 6.2 负载均衡原理

```
Topic: ai.review.tasks (6 个分区)
                                ┌─────────────────┐
                                │   Kafka 分区分配   │
                                └────────┬────────┘
                                         │
          ┌──────────────────────────────┼──────────────────────────────┐
          │                              │                              │
   Python 实例1                   Python 实例2                   Python 实例3
   (分区 0, 1)                    (分区 2, 3)                    (分区 4, 5)
          │                              │                              │
   跑 LangGraph                   跑 LangGraph                   跑 LangGraph
   回调 Java                      回调 Java                      回调 Java
```

- 同一个消费者组 `python-review-workers`，Kafka 自动分配分区
- 加实例自动触发 rebalance，不需要改配置
- 每个 Python 实例独立跑 LangGraph，互不干扰
- 一台 Python 处理的 TPS = 1 / LangGraph 耗时，N 台就是 N 倍

### 6.3 对比原方案

| | 原方案（Java 消费 Kafka + HTTP 调 Python） | 现方案（Python 直连 Kafka） |
|--|------------------------------------------|--------------------------|
| 链路长度 | Java → Kafka → **Java 消费者** → HTTP → Python → 回调 | Java → Kafka → **Python 消费者** → 回调 |
| 消费者线程 | Java 线程池有限，同步等 Python 返回 | Python 自己管理并发 |
| 水平扩展 | 扩 Python 但 Java 消费者线程仍是瓶颈 | 扩 Python 实例即可 |
| 职责划分 | Java 管调度又管消费，边界模糊 | Java 只管投递，Python 只管消费 |

## 七、Python 回调 Java 更新状态

### 7.1 回调安全设计

```java
@PostMapping("/api/internal/review/callback")
public ResponseEntity<Void> callback(
        @RequestBody String rawBody,
        HttpServletRequest request
) {
    // ① Token 认证：简单的共享密钥
    String token = request.getHeader("X-Callback-Token");
    if (!callbackToken.equals(token)) return 401;

    // ② Timestamp 防过期：允许 ±300 秒偏差
    long ts = Long.parseLong(request.getHeader("X-Callback-Timestamp"));
    if (Math.abs(now - ts) > 300) return 401;

    // ③ Nonce 防重放：同一个 nonce 只能用一次
    String nonce = request.getHeader("X-Callback-Nonce");
    if (nonceCache.contains(nonce)) return 401;
    nonceCache.put(nonce, expiresAt);

    // ④ HMAC-SHA256 签名验证
    String sig = request.getHeader("X-Callback-Signature");
    String expected = hmacSign(callbackToken, ts, nonce, rawBody);
    if (!MessageDigest.isEqual(expected, sig)) return 401;

    // ⑤ 反序列化 + 更新状态
    ReviewCallbackRequest cb = objectMapper.readValue(rawBody, ...);
    taskService.handleCallback(cb);

    return 202;
}
```

> **四个校验缺一不可：**
> - Token：你是谁
> - Timestamp：这个请求是不是过期的
> - Nonce：这个请求是不是重放的
> - Signature：这个请求的内容有没有被篡改

SET status = CASE

### 7.3 完整状态流转图

```
                             Kafka                           Python 回调
  ┌───────────┐          ┌──────────┐          ┌──────────┐          ┌───────────┐
  │  PENDING  │ ──────→  │   MQ     │ ──────→  │PROCESSING│ ──────→  │  SUCCESS  │
  │ (Outbox)  │          │ (Topic)  │          │ (Python) │          │           │
  └───────────┘          └──────────┘          └──────────┘          └───────────┘
                                                                           │
                                                                    ┌──────┴──────┐
                                                                    │             │
                                                               ┌─────────┐  ┌──────────┐
                                                               │  FAILED │  │HUMAN_    │
                                                               │ (异常)   │  │REVIEW    │
                                                               └─────────┘  └──────────┘
                                                                                 │
                                                                           人工审批
                                                                           │
                                                                     ┌──────────┐
                                                                     │ APPROVED │
                                                                     │ /REJECTED│
                                                                     └──────────┘
```

| 状态 | 含义 | 发生时机 | 数据写入 |
|------|------|---------|---------|
| `PENDING` | 任务已创建，等待投递 | `publishAsync()` 写完 DB 后 | `review_task` + `outbox_event` |
| `PROCESSING` | Python 正在跑 LangGraph | Kafka 分配给 Python 实例后 | `review_task.status` 更新 |
| `SUCCESS` | 审查完成，不需要人工介入 | Python 回调成功，`needHumanReview=false` | `review_task` + `review_result` |
| `HUMAN_REVIEW` | 需要人工审批 | Python 回调成功，`needHumanReview=true` | `review_task` + `review_result` |
| `FAILED` | 异常终止 | Python 超时/错误/回调失败 | `review_task` + `review_result.error` |
| `APPROVED/REJECTED` | 人工决定 | Handoff 接口调用 | `review_task.handoff_*` |

## 八、索引优化总结

### 现状索引

| 表 | 索引 | 设计理由 |
|----|------|---------|
| `review_task` | `idx_review_task_status_mode (status, mode)` | 状态+模式联合查询 |
| `review_task` | `idx_review_task_project_status (project_id, status, created_at)` | 项目维度的状态查询（覆盖索引） |
| `review_task` | `idx_review_task_created_at (created_at DESC)` | 游标分页 |
| `review_result` | `idx_review_result_task_id (task_id) UNIQUE` | 1:1 关系约束 |
| `review_result` | `idx_review_result_task_created (task_id, created_at)` | 按任务查结果 |
| `outbox_event` | `idx_outbox_status (status, created_at)` | 轮询 PENDING 事件 |
| `outbox_event` | **建议改为部分索引** | 避免历史 SENT 行膨胀 |

### 优化经历

> **场景**：上线初期 `outbox_event` 表数据量小，`idx_outbox_status (status, created_at)` 表现正常。运行一个月后，`SENT` 行积累到 200 万+，虽然查询只扫 `PENDING` 段，但 B+树索引文件膨胀到 200MB+，缓冲池命中率下降。
>
> **方案**：改为 MySQL 8.0 部分索引 `CREATE INDEX idx_outbox_pending ON outbox_event(created_at) WHERE status = 'PENDING'`。
>
> **效果**：索引从 200MB 降到 ~5MB（只存 PENDING 行），查询更快，`SKIP LOCKED` 页锁冲突减少 70%。

## 九、最终一致性兜底

```sql
-- ReconciliationJob 每分钟执行
-- ① 扫描卡住的 PENDING 任务（超过 30 分钟）
SELECT * FROM review_task
WHERE status = 'PENDING'
  AND created_at < NOW() - INTERVAL 30 MINUTE
LIMIT 50;

-- ② 扫描卡住的 PROCESSING 任务（超过 2× 超时时间）
SELECT * FROM review_task
WHERE status = 'PROCESSING'
  AND updated_at < NOW() - INTERVAL (asyncTimeoutMs * 2) MILLISECOND
LIMIT 50;
```

- PENDING 卡住 → 重建 `outbox_event`，设置 `event_type = 'TASK_RECONCILED'`，重新投递
- PROCESSING 卡住 → 直接标记 `FAILED`，写入错误原因 `RECONCILIATION_TIMEOUT`
- 兜底不是主流程，是最后一道防线。正常情况下不应触发





## 对数据库的压力

 我顺着全链路数一遍，每个任务到底写多少次 DB。

  Searched for 1 pattern (ctrl+o to expand)

● 逐次数

  一个异步任务正常走完，对 DB 的精确操作：

  第 1 步：publishAsync（同一事务，4 次写）

  INSERT review_task                     → 写
  INSERT review_task_payload (有diff)    → 写
  INSERT outbox_event                    → 写
  INSERT task_audit_log (null→PENDING)  → 写

  第 2 步：OutboxPoller 投递 Kafka

  SELECT ... FOR UPDATE SKIP LOCKED     → 读（20条一批，均摊 ≈ 0.05 次/任务）
  UPDATE outbox_event SET status='SENT' → 写

  第 3 步：processAsyncTask

  SELECT consumed_message (幂等检查)     → 读
  SELECT review_task (查任务是否存在)      → 读
  UPDATE review_task SET status='PROCESSING' → 写
  INSERT task_audit_log (PENDING→PROCESSING) → 写
  INSERT consumed_message (记录已消费)     → 写

  第 4 步：Python 返回 → 状态落库

  UPDATE review_task SET status='SUCCESS' → 写
  INSERT INTO review_result ... ON DUPLICATE KEY UPDATE → 写（Upsert）
  INSERT task_audit_log (PROCESSING→SUCCESS) → 写

  总计

  写入：4 + 1 + 3 + 3 = 11 次
  读取：2 次

  压力模拟

  MySQL 单机 IOPS 一般在 1000-5000（取决于磁盘类型）。按平均 2000 IOPS 算：

  每任务 ≈ 13 次 IO（11写+2读）
  2000 / 13 ≈ 153 TPS

  理论上限大约 150 TPS。

  不同吞吐下的压力：

  ┌─────────┬───────────┬───────────────────┬───────────────────┐
  │  吞吐   │  每秒 IO  │    DB 写入频率    │     压力感受      │
  ├─────────┼───────────┼───────────────────┼───────────────────┤
  │ 1 TPS   │ 13 IO/s   │ 几乎无感          │ 0.7% 的 2000 IOPS │
  ├─────────┼───────────┼───────────────────┼───────────────────┤
  │ 10 TPS  │ 130 IO/s  │ 每 77ms 一次写入  │ 无压力            │
  ├─────────┼───────────┼───────────────────┼───────────────────┤
  │ 50 TPS  │ 650 IO/s  │ 每 15ms 一次写入  │ 中等负载          │
  ├─────────┼───────────┼───────────────────┼───────────────────┤
  │ 100 TPS │ 1300 IO/s │ 每 7.7ms 一次写入 │ 有明显压力        │
  ├─────────┼───────────┼───────────────────┼───────────────────┤
  │ 150 TPS │ 1950 IO/s │ 每 5ms 一次写入   │ 接近上限          │
  └─────────┴───────────┴───────────────────┴───────────────────┘

  问题在哪

  不是量的问题，是写法的分布：

  -- 第 1 步：一个事务里 4 次写
  -- 第 3 步：3 次分散的写入（不在同一事务）
  -- 第 4 步：3 次写（也不在同一事务）

  理想情况：第 3 步的 PROCESSING 和第 4 步的 SUCCESS 如果能合并成一个事务，能省 2 次 UPDATE + 2 次 task_audit_log 写入。可惜它们是跨进程的（Java
  消费者线程和 Python 回调），合不了。

  面试话术

## 十、面试背诵要点简表

| 面试官问 | 回答要点 |
|---------|---------|
| 数据怎么从用户到后端 | 路由决策（特征提取 → 直接规则 → 边界分类器） |
| 状态怎么流转 | PENDING → Kafka → PROCESSING → 回调 → SUCCESS/FAILED/HUMAN_REVIEW |
| 怎么保证不丢消息 | Transactional Outbox，同一事务写 DB + 事件 |
| 怎么保证不重复处理 | `consumed_message` 表 + Kafka offset 手动提交 |
| 怎么负载均衡 | Python 消费者组，Kafka 自动分区分配 |
| 回调安全怎么做的 | Token + Timestamp + Nonce + HMAC 签名四层校验 |
| 索引怎么优化的 | 部分索引 `WHERE status='PENDING'`，缩小小 20 倍 |
| 数据一致性谁兜底 | ReconciliationJob，扫描卡住任务重建/标记失败 |
| 为什么选 Outbox 不选 2PC | 性能好，简单可靠，不需要协调者 |
