## 事故介绍

所有数据来自互联网公开数据。

2025-1-16 14:40开始，一部分用户发现在支付宝内进行支付时，发现订单被优惠减免了20%的金额。意味着原本你买一个手抓饼可能100块，用支付宝直接省20。而且这不仅限于支付订单，转账订单也可以享受这个优惠。

支付宝方面很快反应，在14:45时完成了故障修复，并且在2025-1-17 1:00发出声明，称不会对享受到这个优惠的用户追回资金。

### 产生原因分析

在支付宝的通告里，产生这个事故的原因是"某个常规营销活动后台配错了营销模板"。

一般一个新的活动功能的上线，可能需要程序员开发新的功能，然后将功能里需要使用的规则，做成配置，配置在营销中心的管理后台上。当然对于一些比较成熟的活动，也可以直接复用以前的代码，只需增加配置即可。

#### 需要开发的新活动

正常流程：程序员提前告诉运营在配置中心建好规则，并且将灰度人群置为0。然后程序员发布新代码。

举一个实际的例子，程序员在服务demo order service里开发了新功能，需要发布上线。demo order service假设有1000台机器，运营在营销中心配置几个灰度账号，用来验证在线上发布后功能是否正常。

在灰度发布阶段，会先选择几台机器做灰度：

```
- 第一批次 3台
- 第二批次 7台
- 第三批次 5%
- 第四批次 10%
- 第五批次 20%
- 第六批次 35%
- 第七批次 全量发布剩下所有的机器
```

根据支付宝解决故障只花了5分钟，可以推测出应该是在第一批次时就发现了问题，并且采取了止血措施。那么受到影响的流量就是0.3%-1%。

##### 亏了多少钱

```python
# 以下单位亿元
# 23年移动支付555万亿，增速11%
5550000 * 1.11 = 6160500
# 24年平均日交易额
6160500 / 365 = 16878.08
# 12月移动支付日交易额（考虑增长）
16878.08 * 1.22 = 20561.26
# 支付宝在移动支付市场份额约60%
20561.26 * 0.6 = 12336.76

# 受影响金额计算
# 单位亿元
12336.76 * 0.01 * 0.2 * 5 / 60 / 24 = 0.0857
# 即亏损金额不超过857W

# 考虑薅羊毛放大系数1.5
# 单位万元
857 * 1.5 = 1286
```

#### 不需要开发的老活动

如果是不需要开发的老活动，运营直接在运营中心改配置即可让活动生效。

```python
# 单位万元
1286 * 100 = 128600
```

但资损不会超过资金池配额。

### 事故总结

新功能上线时需要面临的问题：

1. 功能开发时要做好监控，能够监控出功能异常的流量并及时报警（本次事故里得满分）
2. 做好发布前的配置检查，配置上线一定要有审批，开发要和实际的配置操作人确认（本次事故得0分）
3. 发布前要做好降级预案，必须要保证当功能出现异常时能降级（本次事故表现满分）

### 背锅分析

- 运营：作为直接引发本次事故的责任人，主要责任
- 开发功能的程序员：作为服务的owner，应该再发布前确认配置正确
- 运营的老板：审核了运营配置
- 测试：连带责任
- 程序员的老板：连带责任
