# Ticket Demo Business Risk Validation Design

**Date:** 2026-05-30

## 背景

当前 `D:\AIPRO` 已经具备业务风险审查链路的三层结构：

- 前端提供业务风险源码上传页与任务观察页
- Java 负责上传接收、预处理、任务推进、派发门禁与观测
- Python 负责消费结构化 `source_package` 并输出业务风险分析结果

用户要求在 `D:\demotest` 下提供一套小型 Java 购票系统源码样本，并通过浏览器里的前端上传页实际验证这条链路是否可用。目标不是只证明“一次成功提交”，而是把这套验证做得更接近生产：需要覆盖超时、重连、日志追踪、错误定位与稳定重复验证；如果发现问题，要沿链路持续修复，直到 fresh run 下稳定可用。

## 目标

交付一套可重复执行的业务风险验收方案，包含两部分：

1. `D:\demotest` 下的 6~8 个 `.java` 文件源码样本
2. 基于 `D:\AIPRO` 现有业务风险上传页的端到端验证与修复流程

验收目标不是 demo 可运行，而是满足以下要求：

- 前端上传页可以稳定提交购票源码样本
- Java 能成功接收 multipart 请求并产出任务
- Java 预处理、budget、dispatch gate、Python worker 分析可以跑通
- 任务观察页/结果页能持续追踪状态与结果
- 页面刷新、轻微断连、慢处理等情况下仍能继续观察
- `traceId` 能贯穿前端、Java、Python，支持排障
- 审查报告能明确识别多类购票业务风险，而不是空泛结果
- 如果链路失败，能定位到具体层，而不是停留在“提交失败”
- 业务风险审查链路必须达到生产级别可用；如果当前不可用，修复目标不是“勉强跑通”，而是修到生产级别可用

## 非目标

以下内容不在本次范围内：

- 把 `D:\demotest` 做成可运行或可部署的 Spring Boot 服务
- 构建完整数据库、消息队列、认证体系或真实支付系统
- 对 `D:\AIPRO` 做与业务风险链路无关的重构或性能优化
- 把验证扩展成全平台全面压测

## 总体方案

### 1. Demo 作为高信号输入样本

`D:\demotest` 中的购票系统只承担一个角色：为业务风险审查链路提供真实、紧凑、可重复上传的高信号源码样本。

这套样本不追求运行，而追求：

- 文件结构符合真实 Java 业务项目外观
- 风险集中在可追踪的业务调用链中
- 方法、依赖、事务边界、缓存/外部调用信号足够明显
- 上传体量足够小，便于多次重复验证

### 2. AIPRO 作为被验证平台

实际验收不通过脚本或直调接口绕开页面，而是以浏览器里的业务风险上传页作为主入口：

- 填写 metadata
- 上传 `.java` 文件
- 提交任务
- 观察任务推进
- 查看结果页/任务详情
- 验证刷新、断连、重试与错误定位能力

### 3. 以 fresh run 作为完成标准

任何“已经修好”的判断，都必须来自新的完整上传验证，而不是只看代码修改、单层日志或旧任务状态。

## Demo 文件结构

Demo 规模固定为 6~8 个 `.java` 文件，推荐结构如下：

1. `TicketController.java`
2. `TicketOrderService.java`
3. `InventoryRepository.java`
4. `OrderRepository.java`
5. `PaymentClient.java`
6. `CacheClient.java`
7. `TicketOrder.java`
8. `CouponService.java`（如需要用于补充外部依赖与优惠券语义）

### 结构意图

- `controller`：制造入口语义与请求流向
- `service`：集中埋入大部分业务风险
- `repository`：制造库存、订单、持久化信号
- `client`：制造支付、缓存、外部调用语义
- `model`：提供订单/票务领域对象名称，帮助风险推理聚焦

## 风险植入设计

风险不会平均分布，而是围绕单条真实购票路径聚集：

`submitOrder -> checkStock -> reserve -> createOrder -> charge -> updateCache -> notify`

### 必须覆盖的风险类型

1. **超卖 / 并发竞态**
   - 先查库存再扣减
   - 缺少原子更新、锁或版本控制

2. **重复下单 / 幂等缺失**
   - 同一用户重复提交时，没有 requestId / token 去重

3. **事务里外部调用**
   - 在事务中直接调用支付或优惠券外部服务
   - 暗示长事务、部分成功、回滚不一致

4. **缓存 / 数据库不一致**
   - 更新缓存与落库顺序错误
   - 落库失败后没有回滚缓存

5. **双写一致性问题**
   - 订单状态更新与通知发送没有 outbox 或补偿

6. **异常吞掉**
   - 捕获关键异常后继续主流程
   - 导致“页面显示成功，但系统内部部分失败”

7. **补偿缺失**
   - 扣库存成功后支付失败，没有回补库存

8. **审计 / trace 断裂**
   - 方法间不显式透传请求标识，便于验证平台侧追踪补齐能力

### 风险集中位置

`TicketOrderService.java` 是主热点文件，负责汇聚：

- 事务边界
- repository 调用
- 支付 client 调用
- 缓存更新
- 通知/副作用触发
- 异常处理

这样 Java 预处理和 Python worker 更容易抽出方法热点、调用边与候选风险路径。

## 上传与验收主路径

### 预备条件

在每次正式验收前，先确认：

- 前端已启动并可打开业务风险上传页
- Java 后端已启动且健康检查正常
- Python worker 已启动且 health/heartbeat 正常
- 页面指向当前运行中的 Java 网关

### 正式流程

1. 打开前端业务风险上传页
2. 填写最小 metadata：`projectId`、`repo`、`branch`
3. 选择 `D:\demotest` 下全部 `.java` 文件
4. 提交上传
5. 记录并观察 `taskId`、`sessionId`、`traceId`
6. 进入任务详情页或结果页持续观察状态变化
7. 等待完成后检查结果是否明确识别多类购票风险

### 页面侧必须成立的行为

- 提交后能拿到任务标识
- 任务标识在页面跳转或刷新后仍可继续追踪
- 任务页在 SSE 中断时能恢复观察能力（自动重连或退回轮询）
- 慢处理时用户不会失去定位线索
- 错误提示能区分校验失败、链路失败与分析失败

## 生产式韧性验证

本次不是只看 happy path，而是重点验证接近生产的问题处理方式。

### 1. 慢处理 / 超时

如果 Java 预处理或 Python 分析变慢：

- 前端不能把任务直接丢失
- 用户必须仍能拿到 `taskId` / `traceId`
- 任务页必须还能继续观察状态
- 日志中必须能沿 `traceId` 查到处理位置

### 2. 断连 / 重连

如果任务页观察期间发生 SSE 中断、页面刷新或临时网络波动：

- 页面应恢复到可继续观察的状态
- 至少要保留跳回任务详情的路径
- 不能要求用户重新上传才能看到旧任务结果

### 3. 派发与 worker 可用性

如果 heartbeat 过期、worker 不可用或 dispatch gate 拒绝：

- 失败必须可见
- 状态或错误信息必须能指向 worker/dispatch 层
- 不能表现为无反馈卡死

### 4. 日志追踪

`traceId` 是整条排障主线，必须能用于串联：

- 前端请求
- Java 上传接收与任务创建
- Java 预处理与派发
- Python 分析
- Java 结果写回 / 任务收敛

## 修复策略

修复工作严格分成两条线：

### 1. Demo 样本线

当问题来自样本本身时才修改 `D:\demotest`：

- 风险信号过弱
- 文件结构不利于预处理
- 报告无法稳定抽出核心调用链
- 语义不够真实，导致分析结果漂移

### 2. 平台链路线

当问题来自上传或审查平台时修改 `D:\AIPRO`：

- 上传页 multipart 提交问题
- Java metadata / 文件校验问题
- Java 预处理或 budget 问题
- dispatch gate / worker heartbeat 问题
- Python worker 输入适配或结果输出问题
- 任务详情页 / 结果页 / 观察恢复问题
- trace/log 贯穿问题

### 修复优先级

1. 阻断上传或任务创建
2. 阻断派发或 Python 分析
3. 阻断任务观察或结果查看
4. 结果质量不足
5. 可观测性缺口

默认优先根因修复，不做与当前目标无关的顺手重构。

## 验证方法

### 基础验证

- 新上传一次 demo 文件
- 确认任务被创建
- 确认任务可推进到终态
- 确认结果页/详情页可见

### 韧性验证

至少覆盖以下场景：

- 页面刷新后继续观察同一任务
- 轻微断连后恢复观察能力
- 慢处理时仍能保留任务与 trace 线索
- 至少触发一种失败场景，并能清晰定位失败层级

### 结果质量验证

报告中应明确体现多类购票业务风险，例如：

- 库存超卖风险
- 重复下单风险
- 事务与外部调用耦合风险
- 缓存与持久化不一致风险
- 补偿或异常处理缺陷

不接受“成功但结果空泛”作为完成标准。

## 完成标准

只有同时满足以下条件，才算这次工作完成：

1. `D:\demotest` 中存在一套 6~8 文件的小型购票源码样本
2. 该样本能通过前端上传页成功提交
3. fresh run 下任务能稳定穿过 Java 与 Python 链路
4. 任务详情/结果页可以持续观察结果，不会因刷新或轻微断连失去上下文
5. `traceId` 能支撑跨层日志定位
6. 报告能明确识别多类购票业务风险
7. 如果链路失败，也能快速定位到前端、Java、dispatch/worker 或 Python 的具体层
8. 业务风险审查链路在本次验收范围内达到生产级别可用，而不是只在单次演示中偶然成功
9. 若当前链路未达到生产级别可用，工作范围自动包含沿前端、Java、dispatch/worker、Python 各层持续修复，直到达到该标准

## 实施顺序

1. 在 `D:\demotest` 创建初版购票源码样本
2. 启动并检查 `D:\AIPRO` 前端、Java、Python 链路
3. 通过浏览器上传源码样本，进行第一次 fresh run
4. 按观察结果修复样本或平台问题
5. 重复 fresh run，直到满足完成标准
6. 对最终结果做一次完整验证，记录关键现象与故障定位依据

## 风险与取舍

- 选择小型样本是为了高频验证与快速定位，不是为了模拟完整业务系统
- 不要求 demo 可运行，避免把精力误投到无关基础设施
- 主入口固定为浏览器上传页，避免接口绕行导致“链路可用性”被高估
- 完成标准强调 fresh run 与可观测性，避免只凭一次偶然成功判断稳定
